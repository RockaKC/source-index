# Source Index export

Rebuilds the site's data from the Kingdom Code SQLite database.

```
python3 tools/export_site.py /path/to/kc_v13.db --check   # show what would change, write nothing
python3 tools/export_site.py /path/to/kc_v13.db           # rebuild data/site.js + bible/
```

Needs Python 3 only. No packages.

## Code layout

The site is static: no build step. `index.html` is the page frame (header, menu, footer, support window) and loads, in order:

- `css/site.css`: all styles.
- `profiles/site.js`: the product profile (see "Product profiles" below).
- `data/site.js`: the page data, `const D = {...}` (written by the exporter; never edit by hand).
- `js/*.js`, plain scripts that share the page's global scope, one per feature:
  - `core.js`: shared helpers, local storage, the Back link, and the **route registry**.
  - `text.js`: Bible text by translation (`loadBook`), verse lookup, numbering notices.
  - `words.js`: the Hebrew and Greek word entries.
  - `essays.js`: Kingdom Code essays, the cited-in-essays section, question paths, the essay page, the call-to-action tool.
  - `search.js`: reading a typed reference, suggestions, title search.
  - `reader.js`: the 81 books, book pages, chapters, verses, passages.
  - `readerbar.js`: the app's reading tools: the chapter bar in the header, the toolbar at the bottom of a chapter (back and forward through this visit's chapters, top of the chapter; it hides while scrolling down), reading history (`kc-history` on the phone, the `#/history` page). Does nothing on a page without the `#readbar` markup, so the site is untouched.
  - `marks.js`: the app's verse panel (tap a verse: favorite, highlight, copy, share) and the Favorites and Highlights pages. A reader's marks are one object on the phone (`kc-marks`, keyed by verse "book id:chapter:verse" in the house numbering); a note is the same record's `n` (up to 2000 characters, written in the same panel; leaving the box in any way saves it, and deleting asks twice). The panel stays open after a choice (Favorite, a highlight, Copy), shows what was set on its buttons and answers in a line inside itself, and scrolls the verse above its top edge; it closes on the close button, Escape, a tap outside, or Back. Copy and Share add the source line ("Genesis 1:1 (Septuagint)", and the English number where a book is numbered differently). Share uses the phone's share sheet (`@capacitor/share`), then the browser's, then copies. Does nothing on a page without the `#sheet` markup.
  - `backup.js`: Back up and restore (`#/backup`). A backup is one JSON file, `{app, version, saved, marks, history}`. Saving on the phone writes it into the app's private cache (`@capacitor/filesystem`, no storage permission) and opens the share sheet (`@capacitor/share`); in a browser it downloads; if neither works it shares or copies the text, which the page can also restore from ("Paste a backup instead"). Restoring shows what it would do and changes nothing until confirmed; it only ADDS: for a verse on both, the newer record wins, history is the union, nothing on the phone is removed. Entries the app could not have written (a chapter that does not exist, an unknown highlight, a key that is not `book:chapter:verse`) are skipped, a note is cut to 2000 characters, and a backup from a newer `version` is refused. Bump `BACKUP_VERSION` only when the file's shape changes in a way an older app cannot read.
  - `guide.js`: Names profiles and the translation tier list.
  - `pages.js`: home, About, Sources and credits, not found.
  - `analytics.js`, `chrome.js` (menu, support window, theme), `offline.js` (install and offline reading).
  - `router.js`: draws the page for the current address. Loaded last, it starts the app.

**Adding a page or a section.** In the feature's file (or a new `js/<feature>.js`), write a view function that returns the page HTML and register it: `addRoute('name', p => viewName(p[1]))` answers `#/name/...` (`p` is the address split on `/`). Wiring a page needs after it is drawn (forms, buttons) goes in `onPage(p => { ... })`. A new file also needs a `<script src="js/<feature>.js?v=0">` tag in `index.html` and `app.html`, at the same place, before `router.js`, and an entry in `PRECACHE` in `sw.js`; a file's top-level code may only use names from files loaded before it.

**After editing anything in `css/` or `js/`**, run `python3 tools/stamp_assets.py`: it refreshes the `?v=` content stamp on each tag so a browser never mixes a new page with an old file. The exporter runs it too. The tests fail on a stale stamp or a file missing from `PRECACHE`.

### Product profiles

One code base serves two products. Each page at the root loads one profile before anything else, and the shared code asks the profile instead of the page:

| Page | Profile | Product |
| --- | --- | --- |
| `index.html` | `profiles/site.js` | Kingdom Code Source Index: the essays sit beside the Bible text. |
| `app.html` | `profiles/app.js` | KC Tewahedo Bible (and the Android app): the Bible first; the essays live in their own section, From Kingdom Code (`#/kc`), and never inside the Bible text. |

The switches: `name` (the product's name, on the app's About page and as the fallback page title), `home` (`'site'` or `'reader'`: which home page), `essaysInBible` (cited-verse highlights, essay lists and essay counts on book, chapter, verse and passage pages, and essay suggestions in search), `analytics` (visit counts) and `readerTools` (the app's chapter bar, reading toolbar, reading history and `#/find` search page) and `verseTools` (the verse panel, favorites, highlights, notes, and back up and restore). Every route works in both products; the app adds `#/guide` and `#/kc` to its header and menu. To change what a product shows, add a switch to both profile files, read it as `PROFILE.<name>` where the feature is drawn, and add a test to `tests/app.spec.js` for the app side. A third product is a new `profiles/<id>.js` and a new page copied from `app.html`; add the page to `PAGES` in `tools/stamp_assets.py`.

The two pages must load the same files in the same order after their profile; the tests check it. `app.html` is not linked from the site and asks search engines not to index it: it is the preview of the app until the Android build ships. Installed from the browser, the site keeps its own name, Kingdom Code Source Index (`manifest.webmanifest`); KC Tewahedo Bible is the name of the Android app only.

## The Daily Witness

One passage a day, each a step in a larger study (`js/witness.js`, website only; `PROFILE.witness`). A front-page card shows today's study (title, passage and translation, a short observation, a link); each study has a page (`/witness/<n>-<slug>/`) with the passage, where it sits, a concise investigation, cross-references with the reason for each, a one-line takeaway, and links to read the chapter, to the essays that cite the passage, and to related Kingdom Code work; `/witness/` is the archive, with the studies grouped into sequences and a canon-coverage board.

- **The schedule is editorial.** `tools/witness.json` is written by hand: `schedule` (`start` = the date study 1 is shown, null until approval; `timezone` = the one time zone whose calendar date decides the day, so every reader sees the same study), `threads` (named sequences), `groups` (the canon's divisions, for coverage), and `entries`. An entry has `n`, `slug`, `status` (`draft` or `approved`), `thread`, `builds_on`, `title`, `observation`, `passage` (one to three stretches of one chapter of one book), `context`, `investigation`, `crossrefs` (reference, reason, optional checked quotation), `related` (essay ids, guide, Early Church, name and word slugs) and `takeaway`. Study 1 shows on `start`, study 2 the next calendar day, and so on; once the schedule runs out the card keeps showing the latest study. Nothing is generated and nothing is chosen at random.
- **No unchecked Scripture.** Every quotation in the prose is written `[[Reference|the words]]`; `tools/witness.py` (run by `tools/export_site.py`) refuses it unless the words are in the stored text of that reference. `[[Reference]]` alone is a link. A quotation mark outside that markup is refused. The Bible text is never copied: a study reads its passage from the archive's own book files, as the verse pages do. References use the stored numbering (the Septuagint's for most of the Old Testament), and each shows the book's house translation and its source.
- **Coverage and repetition.** The exporter refuses a verse used as the passage of two studies, the same book on two days running, or the same book more than twice in any seven studies. `python3 tools/witness.py coverage` reports which books of the canon the studies have been about or cross-referenced, group by group, and which entries of the 81 still have no stored text. The archive shows the same board.
- **Public only when approved.** A `draft` is shown only to a browser that opened any page with `?witness-preview=1` (off again with `=0`); that switch hides drafts from the page and is not access control, and the plan is in this public repository either way. A study goes public when its status becomes `approved` and the schedule has a `start`. Approved studies are in the sitemap and are prerendered as real pages; the card, the archive and the neighbours follow the date.
- **Output.** `D.W` (the index, in `data/site.js`) and `data/witness/<n>.json` (the study) are written by the exporter, and so is `tools/witness_review.md`, the whole schedule with each passage's stored words, for reading it before approval. Do not edit them by hand.
- **Later.** Saving a study to My Library needs `witness` added to the `kind` check in `supabase/schema.sql` and a `witness` kind in `js/account.js`.
- **Tests** (`tests/witness.spec.js`, `tests/witness_check.py`): the committed files match the plan; every kind of unchecked word or broken schedule is refused; every quotation is in the stored text; the date logic across clock changes and time zones; draft, preview and approved states; the card, study, archive and coverage; clean addresses and the sitemap; phone widths in both themes; the prerendered pages.

## Berean reader accounts

`js/account.js` (website only; the app loads the file but it does nothing there): **Become a Berean** (`/become-a-berean/`), **My Library** (`/my-library/`), a **Save** button on essays, guides, chapters, verses and passages (on a chapter page, tapping any verse, or its number, opens a small Save bar under it; a cited verse's words still open its page, and Space on the focused link opens the bar), and **Privacy** (`/privacy/`). The archive stays open to everyone; an account only gives a reader a private shelf. Everything is off until `profiles/site.js` sets `accounts: {url, key, public}`; with `public: false` it is a private preview, visible only in a browser that opened any page with `?berean-preview=1` (off again with `=0`), so it can be tested against the live Supabase project before launch. `supabase/email-template.html` is the sign-in email (code only, no link). The settings are the Supabase Project URL and *publishable* key, both public by design; never the secret or service_role key). Optional: `turnstileKey` (Cloudflare Turnstile site key), `codeLength` (default 7) and `codeMinutes` (default 10), which must match Supabase's email settings.

- **Sign-in** is Supabase Auth with the official `supabase-js` (`vendor/supabase.js`, pinned, see `vendor/README.md`), fetched only on account pages or for a reader who already has a session (`kc-session` in local storage). The reader types their email, receives a one-time code, types it back; the emailed link also works. The emailed link returns to `SITE_ORIGIN + /my-library/`, so it follows `origin` in `profiles/site.js`; list the same address in Supabase, Authentication, URL Configuration.
- **Data** is one table, `saved(user_id, kind, item_key, created_at)`, and one function, `delete_my_account()`; both in `supabase/schema.sql`. Row-level security lets a reader see and change only their own rows. Keys: a guide's slug, an essay's number, or Scripture in the house numbering (`book:chapter`, `book:chapter:verse`, `book:chapter:first-last`).
- **Nothing else is stored**: no name, no profile, no mailing list. Account pages are `noindex` and disallowed in `robots.txt`; the privacy page is indexed.
- **Tests** (`tests/account.spec.js`) simulate Supabase in the browser (`tests/fake_supabase.js`, `page.route`); the site ships no test hook. They cover sign-in with the 7-digit code, the library, saving and removing, signing out, export, deleting the account, Turnstile, the privacy page, and that nothing appears when `accounts` is null.

## The move to kingdomcodearchive.com

The website's address is written once, as `origin` in `profiles/site.js`; canonical links, `sitemap.xml`, `robots.txt`, `llms.txt`, share cards and structured data all read it. Two more places name it: `index.html` (its static canonical link) and `CNAME`; analytics counts only on the hosts listed in `js/analytics.js`. The website was first published at sources.kingdomcodearchive.com.

GitHub Pages serves one custom domain per site and cannot send a 301, and Namecheap's URL redirect record does not carry the path or serve HTTPS, so the old address is kept by a second, tiny Pages site. `node tools/redirect_site.js SITE_DIR OUT_DIR` (SITE_DIR is the prerendered `_site`) writes it: a real file at every old address, each naming the new address as canonical and redirecting at once (query and fragment kept), a `404.html` that does the same for any other address, `sw.js` that removes the old service worker, and a `sitemap.xml` of the old addresses. It refuses to run while `profiles/site.js` still names the old address. Run it once, at the move; the output is published from its own repository and never changes. `tests/redirect.spec.js` covers it.

## Tests

Every pull request runs the tests on GitHub (`.github/workflows/tests.yml`); a red check means do not merge. To run them locally: `npm install` once, then `npm test` (needs Node 22; `npx playwright install chromium` the first time).

- `tests/data.spec.js` checks the exported data without a browser: every book with text has its file and chapters, a translation label and source language; every essay has a link; every cited verse points at a real book and essay; the manifest icons and offline files exist.
- `tests/routes.spec.js` opens every kind of page (every book page, the first and last chapter of every book with text, a cited verse in every cited book, every path, word and name, sample essays, deep links) and fails on a missing heading, an empty chapter or any page error.
- `tests/readerbar.spec.js` covers the app's reading tools: the bar, the toolbar and its trail, the history page, the menu groups, and that the website has none of it.
- `tests/notes.spec.js` covers notes: writing, editing, deleting, keeping a note on leaving the box by every route, the 2000-character limit, and the Notes page (a note is shown as text, never markup).
- `tests/backup.spec.js` covers back up and restore: what is saved, the phone and browser routes, the preview before any change, the merge rules (newer wins, nothing removed), the round trip, and what is refused or cleaned.
- `tests/verse.spec.js` covers the verse panel: opening and closing it (Escape, the close button, Back), favorites, the eight highlights, copy and share and their fallbacks, the Favorites and Highlights pages, and that the website has none of it.
- `tests/bundle.spec.js` builds the Android app's files (`www/`) and opens them the way the app does: see "Android app".
- `tests/app.spec.js` opens `app.html` and checks the app's side of the profiles: the reader home, no essays on book, chapter or verse pages, any chapter reachable from the search box, From Kingdom Code and the Guide, and no analytics.
- `tests/search.spec.js` runs 61 searches and compares the suggestions, the page opened, its heading and notes, and the reading links with `tests/golden/search.json`. When a change is meant to alter them (a database rebuild, new essays, new wording), run `npm run test:update` and read the difference in `tests/golden/search.json` before committing it: that diff is the record of what changed for readers.
- `tests/offline.spec.js` reads a chapter online, stops the server, and checks the page and chapter still open from the saved copy.

## What it changes

- `data/site.js`: the page data, one `const D = {...};` line. `index.html` loads it before the app. Chapters essays cite are inlined here for a fast first page.
- `bible/<translation>/<book id>.json`: every verse of one book in one translation (the book's house translation, lower case: `lxx`, `blb`, `charles`, `platt`), fetched only when a reader opens a chapter or verse that is not inlined. The page reads them through one loader, `loadBook(book, translation)`, so a second translation of a book can sit beside the first later without moving anything.
- `index.html`: only the `?v=` version on its `data/site.js` script tag, a hash of the data file, so a browser never pairs a new page with old data. Nothing else in the file is touched.

Running it twice in a row changes nothing the second time.

## Publication rules

- Only articles with status `published` appear. Draft citations never reach the page.
- A published article with no link yet (it is logged before its post is live) is held back and listed in the report as "no link yet", so the page never gets a dead link. A profile that lists such an article stops the build.
- Quips are left out. `tools/curated.json` lists a few other published articles the page holds back.
- Citations the database marks `review` (unconfirmed numbering) are left out until resolved.
- Jubilees (R. H. Charles, 1902, public domain) is in `kc_v17.db` and is exported like 1 Enoch. Verse numbers are Charles's and can differ from other editions, which the credits page says.
- A citation at a verse missing from the stored text (for example Acts 8:37, which the Berean Literal Bible omits) is still shown as a hit. The verse page lists the essay without verse text, and the report names each one so the database can be checked.
- Raw view counts do not leave the database. The page gets a ranking order only.

## English and Septuagint numbering

The page converts typed English references to the Septuagint numbers the text uses, from `verse_map` in the database. The Psalms have a complete map. Other books have only the verses your published essays cite (dataset `kc_cited_remaps`), so the page marks those books as numbered differently from English Bibles and tells a reader who typed an unmapped number. A book's map is treated as complete only if its English chapters and verses run without gaps.

## Hebrew and Greek lexicon

`tools/import_lexicon.py LEXICON_DIR kc_v15.db kc_v16.db` loads STEPBible's brief Hebrew and Greek lexicons (CC BY 4.0) into a new copy of the database: about 22,700 entries in the `lexicon` table, with the license, credit line and list of changes recorded in `datasets`. The input database is never modified, the output must not already exist, and the source files are not copied into this repository. Each entry is an extended Strong's key such as `H5315G`, so one base number can carry several senses. The site uses it for the word entries in `tools/curated.json`: each form carries a Strong's number in `n` (for example `H5959`). A bare number means the main sense and also lists the other senses; a number with a letter (`H3568A`) names one exact entry, which is how to pick the right sense when a number covers unrelated words. The exporter pulls those entries' text from the database into the page's `LX` data, applies the typographical corrections listed under `lexicon_fixes` in `curated.json`, and adds the "STEP Bible (www.STEPBible.org)" credit to Sources and credits. It stops if any link does not resolve, and it needs a database that has the lexicon loaded (kc_v16 or later). Link by number, not by spelling: matching by transliteration once paired "rib" with a word meaning "to pray".

## Visit counts

The page can count visits without cookies or personal data. It is off until `ANALYTICS` in `index.html` names a provider and a site (`goatcounter` with your GoatCounter code, or `umami` with your website id). While blank it loads nothing and sends nothing.

Counted: page views under readable names (`/verse/Genesis/6/4`); the kind of search made (reference, word, title); searches that find nothing, with the words typed (capped at 60 characters); verses with no essay (`miss/verse`), which is demand for new writing; typed English numbers that could not be converted; clicks out to essays (per essay), Patreon, Substack, Ko-fi, the Android app download (`click/app-download`) and email; and opens of the support window. The Ko-fi form inside the window is Ko-fi's and cannot be counted.

Guards: counts only on the hostnames in `ANALYTICS.hosts` (the live domain, so development is never counted), never when the browser sends Do Not Track or Global Privacy Control, and the internal `#/cta` tool is not counted. When counting is on, Sources and credits tells readers.

## Translation tier list

The page at `#/translations` shows the New Testament translation tier list from `tiers` in `tools/curated.json`: tiers, one line per translation, a how-to-use summary and a link to the full essay. It mirrors the published essay (`essay` is its piece id), so edit the file when the essay changes. The exporter stops if that essay is not a published essay on the page.

## Numbering warnings for partly mapped books

A book with only some verses mapped from English to Septuagint numbers warns on every typed number it has not converted. `numbering_scope` in `tools/curated.json` narrows that warning to the chapters named, for books where most chapters are known to match English. Genesis is listed with chapters 31 and 32: 48 of its 50 chapters have the same verse count as English Bibles, and those two differ (English 32:26 is Septuagint 32:27). A book is added only after its chapters are checked (compare verse counts with the standard English counts, and read the versification table). The exporter stops if a listed book has no partial map or a chapter is out of range.

## Installable app and offline reading

The site installs to a phone's home screen and reads offline. Files at the repo root, all hand-kept (the exporter does not touch them): `manifest.webmanifest` (name, colours, icons), `sw.js` (the service worker) and `icons/` (192 and 512 px, a maskable 512 px, and the 180 px Apple icon, a "KC" monogram in the site's green).

`sw.js`: pages and the page's own files (`data/site.js`, `js/*.js`, `css/site.css`) are fetched network-first, so a reader online always gets the current site and the last copy is only the offline fallback (each file is kept under its plain address whatever its `?v=` stamp, and all are saved when the worker installs, so the site opens offline after a single visit; every file `index.html` loads must be in `PRECACHE`, and a test checks it); Bible text (`bible/<translation>/<id>.json`) is served from the saved copy and refreshed in the background; anything on another origin (analytics, Ko-fi) is left alone. Two caches: `kc-shell-v10` and `kc-books-v2`. Bump `SHELL` in `sw.js` when its caching rules change, and `BOOKS` when the book files move. The site no longer offers its own install button or a save-everything button (the browser's install banner is suppressed): the About page's "Get the app" section sends readers to `#/app`, the download page for the Android app, which carries the whole Bible.

Two analytics events: `app/open` (once per session, when opened from the home screen) and `app/installed`. Test it with a real offline (stop the test server), not Playwright's offline switch, which does not block a service worker's own requests.

## Android app

KC Tewahedo Bible for Android is `app.html` (profile `profiles/app.js`) inside a Capacitor shell: an Android app whose screen is a browser view of files stored on the phone. It is not on any app store; readers download the APK from a GitHub Release. Everything the app shows comes from the same files as the site, so there is no second copy of the code to keep in step.

- `capacitor.config.json`: the app's id (`com.kingdomcodearchive.tewahedo`, permanent: a different id is a different app to Android), its name, and `webDir: www`.
- `tools/build_app.py` gathers `www/`: `app.html` as `index.html`, every file it loads, all of `bible/` (so the whole Bible reads without a connection) and `img/` (the translation tier list's picture). `www/` is rebuilt on every run and never committed. In the app, `js/offline.js` sees `window.Capacitor` and leaves out the offline worker and the install and save buttons, which only the website needs.

**Opening the app.** `MainActivity.java` keeps the launch screen up until the first page has loaded and had a few frames to draw, then fades it away, so the reader goes from the launch screen straight to a drawn page (a page that never loads is released after 3 seconds). The launch screen itself is the icon's own leather green (`launch_background`, an alias of `ic_launcher_background`) with the book on it (`drawable/splash_mark.png`, made by `tools/android_icons.py`: the icon's tile with its leather faded out at the edges, so no plate shows). The window and the page's background are the page's two colours, white and near-black (`splash_background` in `values/` and `values-night/`, equal to `--bg` in `css/site.css`, and the WebView's own background is set from the same resource); `tests/launch.spec.js` checks the resources agree with the stylesheet. The app's first page takes no entrance animation, every later one does (`js/router.js`). If a reader has chosen the opposite of their phone's light or dark setting inside the app, the launch screen follows the phone and fades to the chosen colour.

**Finding citations (`tools/extract_citations.py`).** The editor has no separate citation tool: the Scripture lists in the `citations` table are made with this one. `python3 tools/extract_citations.py kc_v33.db --validate` runs it over every essay that already has citations and compares (on 17 October it found 2,299 of the 2,301 stored citations, and agreed on the resolution and house numbers of 2,285 of the 2,299 shared; the differences are where the earlier work held a verse for review and this tool trusts the mapping table, or the reverse). `--show 1349 1352` prints what it would record for named essays; `python3 tools/extract_citations.py kc_v33.db kc_v34.db --nodes 79 165 ...` writes a new database copy in which those essays' citations are replaced (their offsets refer to the text, which may have changed) with origin `ai`, and logs it in `import_log`. It reads references such as Genesis 6:4, 1 Sam 17:45, Enoch 15:8-12, Psalm 22:16 and John 7:53-8:11 (book names, the abbreviations in `books`, and common variants). **Numbering:** New Testament, Enoch and Jubilees are the English numbers (assumed_same); an Old Testament verse listed in `verse_map` is mapped to its Septuagint number; a chapter the database already treats as unchanged is assumed_same; a book with known numbering differences and a chapter not yet settled is `review`, which the site does not publish and the exporter counts as "awaiting review". A reference the essay itself gives in Septuagint numbering ("Psalm 39:7, Septuagint", or "Psalm 88:7 (Psalm 89:6 in English Bibles)") is already the house number and is not mapped again. Chapter-only references and lists of verses after a comma are not read. Look at `--show` for a new essay before writing.

**Adding Substack posts to the database.** `tools/import_substack_posts.py EXPORT_DIR kc_v32.db kc_v33.db [--replace-text SLUG ...] [--check]` reads a Substack export (Settings > Exports): `posts.csv` and `posts/<id>.<slug>.html` only. **Put only those two things in EXPORT_DIR: the export zip also holds the subscriber list and per-post delivery files, which hold readers' email addresses and are never read, copied or committed.** A published post not in the database becomes a new article (origin `import`, status `published`, its text as Markdown through `tools/substack_md.py`, its address, date, audience and word count); a post whose draft is already in the database (matched by `nodes.external_ref`, `substack:<number>`) is promoted: the draft row becomes a published article with the live title, address, date and text, keeping its citations; `--replace-text SLUG` swaps an essay's text for the version in the export (the old text stays in `node_revisions`). Drafts, podcasts and restacks are never imported. The input database is opened read-only, the output must not exist, everything is one transaction, and `import_log` records it; `--check` writes nothing. **Citations are not created here:** the editor's own tool does that, and an imported or replaced essay shows no Scripture section (or a stale one) until it is run on it. A post that is not open to everyone (`audience` not `everyone`) is stored with that audience and never gets text on the site; add its id to `exclude_piece_ids` in `tools/curated.json` to keep it out of the lists as well, as for a start page. The converter reproduced the text of 119 of the 161 essays already in the database exactly, and the rest within a few words, which is how it was checked. Links between essays, and to this site, are rewritten to stay on the site (`tools/export_site.py`, `rewrite`).

**Figures in essays and between profiles.** A name in an essay read on the site links to the figure's profile (first mention, only where the database connects that essay to that figure), and a profile lists the figures it connects to with the basis and the verses behind each. The rows, the rules and the SQL to add them are in `tools/KNOWLEDGE.md`; `tools/knowledge.py` reports essays that use a figure's name but are not connected; `tests/figures.spec.js` and `tests/knowledge_check.py` cover it. Proposed rows (`confirmed = 0`) never ship; `KC_SHOW_PROPOSED=1` shows them in a scratch preview build.

**Essay text (website): published essay by essay.** Essays open on the platform where they were published (Substack or Patreon) unless Boss has approved their text for the site. `essay_text_ids` in `tools/curated.json` lists the approved essays (database ids); while it is empty the exporter writes no `essay-text/` folder (it deletes one if it is there), `D.ET` is empty and every list links out. A manuscript is never committed before it is approved: to review one, run the exporter in a scratch copy of the repository with `KC_ESSAY_IDS=1349,181,37` (never in the repository itself, because `data/site.js` and `essay-text/` are committed and published); to publish, add its id to `essay_text_ids` and re-export. For each listed essay the exporter turns the database's essay Markdown (`nodes.body_md`) into page HTML with `tools/essay_text.py` and writes `essay-text/<id>.json`, only for published Substack posts open to everyone (never Patreon posts, members-only posts or drafts). The text is never rewritten: each Scripture reference the author wrote becomes a link to its passage (`link_refs`, from the recorded citations, only where the stored text really holds it at that position and outside any existing link), and the export stops if the page's words differ in any way from the manuscript's (`same_words`). The essay page at `#/essay/<id>` shows the text with the verses it cites below it. **The lists:** the front page's Latest essays, the Essays page (`#/essays`) and the collection count show every essay that cites verses plus every public Substack essay (`D.PUB`, the Substack essays open to everyone), newest first, so a new post appears before its citations are in; it opens on its platform in a new tab, and has a Sources link only when it cites verses. Patreon posts that cite no verse are not listed (the database does not say which are patron-only). The essay page `#/essay/<id>` (verses, words and related essays) is the Sources page that the Sources links open.

**Guides (website).** The website's header has Bible and Guides; Guides (`#/guide`) replaced Words there, and Names and Translations left the burger menu. The Guides page is a short menu, the same list as the app's Guide page: Kingdom Code Guides first (website only), then Names, Words, Translations and the Ethiopian books in English. Kingdom Code Guides (`#/guides`, `viewKcGuides` in `js/guide.js`) lists Kingdom Code's downloadable guides as cards, and each guide has its own page (`#/guides/<slug>`, `viewKcGuide`) with the wide cover, description, the Download PDF and Read online buttons, and "Inside this guide", the contents with page numbers. The data is `kc_guides` in `tools/curated.json`, exported as `D.KG` and switched on by `kcGuides` in `profiles/site.js` (the app leaves it off and keeps its own Guide page). Each guide is a PDF kept in `guides/` and a wide cover image in `img/guides/` (the editor's 16:9 cover art, 1200 pixels wide, as webp). To add a guide: put the finished PDF in `guides/`, add the cover, and add an entry (`slug`, `title`, `sub`, `about`, `file`, `cover`, `pages`, `date`, and `contents`, a list of `{title, page, about}` taken from the PDF's own contents page); run the exporter, which checks the file is a PDF, the cover exists, each contents page falls inside the guide, and records the file's size. The Download button saves the file from the site (`download` attribute) and Read online opens it; both are counted by the site's visit counter (`guide/download`, `guide/read`). Commit a PDF only when it is final: every revision adds a full copy to the repository's history, so keep files under about 5 MB and give a real revision a new file name.

**Website and app download.** The site's download page (`#/app`) shows the app's icon (`img/app-icon.webp`, cut from `android/icon-source.jpg` by `tools/android_icons.py`, which writes it with the launcher icons) and a Download button. The button's address starts as the GitHub Release file; when the site also holds a copy at `download/KC-Tewahedo-Bible.apk`, the page (a same-site HEAD request, `js/pages.js`) points the button there with the `download` attribute, so the file saves from the site without going through a GitHub address. That copy is not stored in the repo: `.github/workflows/pages.yml` assembles the site, fetches the latest release's `KC-Tewahedo-Bible.apk` into `download/`, and publishes it to GitHub Pages. It runs when `main` changes and after every release (the publish job in `android.yml` starts it; that step cannot turn a release red). It needs the repository's one-time setting Settings > Pages > Build and deployment > Source = "GitHub Actions" (it was "Deploy from a branch"); until that is set the workflow's deploy step fails harmlessly, the branch deploy keeps serving the site, and the button keeps the GitHub address. Pages does not run Jekyll for this kind of deploy; the site is plain files, so nothing depends on it. The in-app Update now still downloads from the GitHub Release, which carries the checksum it verifies.

**Early Church (website only).** Guides > Early Church (`js/guide.js`, switch `earlyChurch` in `profiles/site.js`) lists historical figures, each with an image and a short overview, in time order. A figure is one entry in `early_church` in `tools/curated.json`: `slug`, `name`, optional `aka` (other names), `line` (one line), `dates`, `sort_year` (an approximate year, birth where known, used only to keep the list in time order; the exporter sorts by it), `image` with `width` and `height` (a file in `img/early-church/`), `alt`, `overview` (paragraphs), `link_terms` (see Connections) and, when there are links to check and credit, `sources` (title, note, https link; the Primary sources area shows only when a figure has some). Standard for every overview: say who the witnesses are, what survives from the person, and mark what rests on later accounts. Its page, clean address, structured data, sitemap entry and `llms.txt` line follow automatically.

**Essays library (website only).** The Essays page (`js/library.js`, switch `library` in `profiles/site.js`) is a research library: search; ten subjects; topics; the newest essays; and the year archive (`/essays/2026/`). Addresses: `/essays/`, `/essays/subjects/<id>/`, `/essays/topics/<id>/`, `/essays/topics/` (all topics), `/essays/<year>/`, `/essays/collections/<id>/`; an essay's own page is unchanged. The data is `tools/library.json` (hand-kept, reviewed): `categories` (the subjects; **each essay has exactly one**), `tags` (the topics; each essay has one or more; each carries `terms`, a regular expression for the words that mark it, and `links`), `collections` (curated reading paths) and `essays` (essay id to subject and topics). A tag or subject `links` entry points into the rest of the Source Index and is checked when the site is built: `book:Enoch`, `person:enoch`, `word:hell`, `figure:tertullian`, `guide:<slug>`, `path:<id>`, `page:<translations|english|words|church|names>`. A subject's or topic's page shows those links under *In the Source Index*; an essay's page shows its subject, its topics, and the links they lead to that the essay's figures do not already cover. A topic used by fewer than 3 essays has no page and is left out. The exporter fails if a listed essay is not in `library.json` or names an unknown subject or topic, so a new essay cannot ship unfiled: run `python3 tools/library.py kc_vNN.db --propose` for a first guess, read the essay, and add its line. `python3 tools/library.py kc_vNN.db` audits the file against the essays' full text (tags an essay carries but never mentions, topics it discusses heavily but does not carry); the audit is a prompt for a person, not a rule. Search matches titles, series, subjects and topics, not the essays' text, which is not on the site. A reading collection is an entry in `collections` (`id`, `title`, `line`, `items`: essay ids in reading order); its page and its place on the Essays page appear once one exists, and none do yet.

**Connections (website only).** Essays and historical subjects point at each other (`js/connections.js`, switch `connections` in `profiles/site.js`). A subject's page ends with a separate section, *Featured in Kingdom Code*: the essays that cite or discuss it, each marked Cited or Discussed, cited first, newest first. An essay's Sources page has *Connected in the archive*: chips for its subjects. Both come from one set of pairs, so they cannot disagree, and a pair is counted once. The pairs: for an Early Church figure, `tools/connections.py` reads the published essays' Markdown from the database (read-only) and `tools/export_site.py` writes only the result (`D.EL`) to `data/site.js`; no essay text leaves the database. For a Name (`D.PP`), the pairs are the profile's own essay list. A figure's matching terms are `link_terms` in `tools/curated.json` (`names`, `short` for a name that is also a common word, `works`). Rules: **cited** = the essay names a work by the person (capitalised, exactly as listed) and names the person too; **discussed** = no work, but at least 3 sentences about the person (2 if one is a direct quotation), or the name is in the title; anything less is a passing mention and is never shown. A sentence that names three or more Fathers together is a list and does not count. Only essays the site lists are linked. `python3 tools/connections.py kc_vNN.db` prints every pair and every passing mention with its reason, so a pair can be promoted or hidden by hand with `connection_overrides` in `curated.json` (each needs `as`: cited, discussed or hide, and a `why`). To connect a new kind of subject (manuscripts, biblical books, civilizations): give each subject `link_terms`, add its section to `subjects_from()` in `tools/connections.py`, and add one entry to `SUBJECT_KINDS` in `js/connections.js`; the sections, the chips, the tests and the search-engine tags follow. An essay's structured data also names its cited or discussed figures (`mentions`).

**Clean addresses and search (website only).** The site's pages have permanent addresses (`/bible/john/3/16/`, `/essays/102-the-bible-in-your-hand-is-not-the-bible-jesus-read/`, `/words/virgin/`, `/guides/kingdom-code/the-ungovernable-mind/`), not `#/…`. `js/urls.js` is the one table that maps them: `pathOf('#/verse/…')` and `hashOf('/bible/…')`. The views still build their links as `#/…` and route on that form; `cleanLinks()` gives every link its clean address after each page is drawn and a click goes through `navigate()` without a page load. An old `#/…` address (the links already in published Substack posts) still opens the right page and is tidied to its clean address on load. Only the website does this (`cleanUrls` in `profiles/site.js`); the Android app has no server and keeps `#/…`. The site's public address is written once, as `origin` in `profiles/site.js`; the canonical links, the sitemap, the share cards and the essay call-to-action all read it, so moving the site to another domain is that one line plus the DNS and `CNAME`. Address rules: an essay's page is found by the number at the start of its address, so a changed title never breaks a link; a book is `/bible/<book>/`, a chapter `/bible/<book>/<chapter>/`, a verse `/bible/<book>/<chapter>/<verse>/`, a range `/bible/<book>/<chapter>/<from>-<to>/`. Never rename these once published.

`js/seo.js` writes each page's title, description, canonical address, share card (`img/og-card.png`; a guide uses its own cover), robots tag and structured data (JSON-LD: WebSite with a search action, Article for an essay's Sources page, Book for a guide, DefinedTerm for a word, a breadcrumb trail for all). Search, essay-link and not-found pages are `noindex`. `tools/prerender.js SITE_DIR` runs on every deploy (`.github/workflows/pages.yml`): a browser draws each address in `seoRoutes()` with the site's own code and saves it as `SITE_DIR/<address>/index.html`, so a crawler that runs no script still reads the finished page (text, links, title, description). It also writes `sitemap.xml`, `robots.txt` (search engines and AI crawlers are allowed; `/search/` and `/cta/` are not), `llms.txt` and `llms-full.txt` (a plain-text guide to the site for AI assistants) and `404.html` (GitHub Pages sends it for an address with no saved page; the site opens and draws that address itself). The sitemap gives a page a `<lastmod>` only when the data holds a real date for it (an essay's publication date, a guide's date); every other page has none, never the day of the build. Only a verse that essays cite is saved as a page of its own, so a link to any other verse or passage (the verse page's previous and next, a name's or word study's references, a Daily Witness citation) goes through `scriptureHash()` (`js/core.js`) to its chapter at that verse, and a test checks that every link in every saved page leads to a saved page. None of it is committed. To try it locally: copy the site into a folder and run `node tools/prerender.js <folder>`. The tests' server answers an address with no file the same way (`tests/serve.js`).

**Version and updates.** The release workflow passes the version it is publishing to `tools/build_app.py` (env `KC_APP_VERSION`, 0.0.0 when unset, which marks a preview build), which writes `www/app-version.json`. `js/updates.js` (profile switch `appUpdates`, app only) reads it to show "You have version 1.1.4" on the Updates page (`#/updates`, in the menu's foot) and on About. The Updates page's button asks GitHub's `releases/latest` for the newest `app-v<version>` and says whether the app is up to date, or names the newer version. Inside the Android app it then offers **Update now**: the native plugin `android/app/src/main/java/com/kingdomcodearchive/tewahedo/UpdaterPlugin.java` (registered in `MainActivity`) downloads the release APK into the app's private cache, reports progress (the page draws the bar, `.upprog` in `css/site.css`), checks the SHA-256 that the release lists for the file (the `digest` field of the asset in GitHub's answer), and hands it to Android's installer through the app's `FileProvider`. It refuses any address outside `github.com/RockaKC/source-index/releases/download/app-v…`, follows redirects only over https, and rejects a file whose SHA-256 differs. Android shows its own install screen each time, and installs only a file signed with the same key as the installed app, so a swapped file cannot get in. The first time, Android sends the reader to its settings page to allow the app to install updates (the `REQUEST_INSTALL_PACKAGES` permission, declared in the manifest and named on the download page); Continue then asks again without downloading twice. A release without a listed checksum, a browser, or a preview build falls back to the plain download link. It asks GitHub only when the reader taps the button, never on its own, and sends nothing but the request. The native part has no automated test (there is no emulator in CI): the page's side is tested with a stand-in plugin in `tests/updates.spec.js`, and the first real install is checked by hand on a phone.
- `android/` is the native project, committed. `npx cap sync android` copies `www/` into it. Hand-kept: `app/build.gradle` (version and signing), `res/values/styles.xml` and `res/drawable/splash.xml` (launch screen), `res/values*/` colours. The launcher icons and launch-screen mark come from the editor's artwork, `android/icon-source.jpg` (the Bible with the gold cross), through `python3 tools/android_icons.py` (needs Pillow); to change the icon, run it with the new picture: `python3 tools/android_icons.py new.png`. The website keeps its own KC monogram (`icons/`).
- `.github/workflows/android.yml` builds it on GitHub. A pull request that touches the app, or the Run workflow button on the Actions tab, makes a **preview APK**; ticking "Sign with the release key" on Run workflow makes the signed build instead, as an artifact only, to check the signing secrets (id `...tewahedo.preview`, so it installs beside the real app; unsigned by our key) under the run's Artifacts. To publish a version, open Actions → Android app → Run workflow on `main` and type it in "Publish a release" (for example `1.0.1`); pushing a tag `app-v1.2.3` does the same. Either makes the **release APK**, signed with the Kingdom Code key, and publishes it as GitHub Release `app-v1.2.3` with its SHA-256 and the signing certificate's fingerprint. Each release carries the APK twice: `KC-Tewahedo-Bible-1.2.3.apk`, and `KC-Tewahedo-Bible.apk`, the fixed name the site's download page (`#/app`, `js/pages.js`) links to through `releases/latest/download/`, so the page always gives the newest version without an edit. The version code is `1.2.3` → `10203`, so every release must have a higher version than the last.
- `tests/bundle.spec.js` opens `www/` the way the app does: the Bible reads from the phone's own files, nothing is requested from the network, and no offline worker starts.

To build on your own computer: Node 22, JDK 21 and the Android SDK (Android Studio has both), then `npm install`, `python3 tools/build_app.py`, `npx cap sync android`, and `./gradlew assembleDebug` in `android/`.

**The signing key.** Android only accepts an update signed with the same key as the installed app. Lose the key and no reader can update; they would have to uninstall and install a new app. The key is a file (`kc-release.jks`) and two passwords, held by the editor, backed up in two places (a password manager and an offline copy), and never committed. The workflow reads it from four repository secrets (Settings → Secrets and variables → Actions): `KC_KEYSTORE_BASE64` (the file, base64-encoded), `KC_KEYSTORE_PASSWORD`, `KC_KEY_ALIAS` and `KC_KEY_PASSWORD`. A release tag without them fails before building. To make the key (once, with JDK 21 installed):

    keytool -genkeypair -v -keystore kc-release.jks -alias kc-release -keyalg RSA -keysize 4096 -validity 10000

`-validity 10000` is about 27 years. The base64 for the secret: `base64 -i kc-release.jks` (Mac), `base64 -w0 kc-release.jks` (Linux), or in PowerShell `[Convert]::ToBase64String([IO.File]::ReadAllBytes("kc-release.jks"))` (Windows).

## Reading the Ethiopian books in English

`english` in `tools/curated.json` drives the page at `#/english`, linked from the 81-books page and the home page: which of the 19 books outside the Protestant canon can be read here, which are in every Bible or in English Apocrypha editions, and which are hard to find in English. Each group lists canon entry ids, and the exporter stops unless every one of the 19 appears exactly once. Keep its claims to what can be checked.

## Source language of each translation

Book pages and the reader say what language each text was translated from ("Septuagint, translated from Greek"; "R. H. Charles, translated from Ethiopic (Ge’ez)"). The language comes from `translation_sources` in `tools/curated.json`, one entry per translation in `translation_labels`; the exporter refuses a mismatch and writes `D.TS`. The English page counts the two groups from the data. When a Ge’ez-based translation is added, give it its own key in both blocks.

## Loading a book of text

`tools/import_text.py TEXT.json src.db out.db` loads the text of one book from a JSON file in `tools/texts/` into a new copy of the database: the translation row, a dataset row that records the source, licence and every editorial change, the verses, and the book's house translation. It refuses a book that already has text, a taken translation or dataset code, a gap in the chapter numbers, or an empty verse. The Didascalia (Platt, 1834, from an Ethiopic manuscript) was loaded this way as kc_v27; its dataset notes hold the provenance, the incompleteness of the manuscript, and what has and has not been proofread. After loading, add the translation to `translation_labels` and `translation_sources` in `curated.json`, a credit, and, if the text needs a caution, a note in `book_notes` (`page` shows on the book page; `chapters` maps a chapter number to a note shown only at the top of that chapter).

## Names profiles

The profiles shown at `#/person/<slug>` and listed at `#/names` live in the database (kc_v18 or later): one `nodes` row per profile with type `person` (name, slug, the one-line description in `summary`, the introduction in `body_md`), plus `person_profiles` (order on the Names list), `profile_groups` (the groups under "In Scripture"), `profile_refs` (verse links, in the stored text's own numbering) and `profile_essays` (the curated essays, in order). Only profiles with status `published` reach the page, so a profile can be drafted in the database first. The exporter stops if a verse is not fully in the stored text or an essay is not published on the page, and it refuses a database without these tables.

`tools/import_profiles.py PROFILES.json kc_v17.db kc_v18.db` made that move once, from the former `people` section of `curated.json`, into a new copy of the database. Keep one working copy of the database from then on, so profiles are not lost between versions. Text is written and approved by the editor.

## Editing the database

Text changes to database content (a profile's wording, a title) go through `tools/patch_db.py`: write the edit as plain SQL in `tools/patches/<date>-<name>.sql`, with a first comment line giving the reason, then run `python3 tools/patch_db.py tools/patches/<file>.sql kc_vN.db kc_vN+1.db`. It writes a new copy, never touches the input, runs everything in one transaction, stops if any statement changes nothing (so a patch cannot be applied twice or to the wrong database), checks integrity, and logs the patch in `import_log`. Old text of an edited node is kept in `node_revisions` by the database's own trigger. The patch files in this folder are the record of what changed and why.
